# Этап 3. To-Be и техническое задание

Карточка этапа методики 3.0. Читается, пока в паспорте проекта «Этап: 3».
Связано: [Ядро](<../README.md>) · [Этап 2](<2-Сбор-данных-и-As-Is.md>) · [Этап 4](<4-MVP.md>) · Стандарты

**Цель:** спроектировать, как будет, превратить это в проверяемые требования и получить утверждённое ТЗ — базу, относительно которой
дальше считается «сделано», «принято» и «изменение».

## 3.1 To-Be
1. Схема To-Be: L — BPMN; S/M — список шагов. Для каждого шага: кто или что делает (человек / n8n / ИИ), система, вход и выход.
2. Для шагов, где рассматривается ИИ, — **ворота** модуля [ИИ-шаги](<../modules/ИИ-шаги.md>). Если ИИ нет — одна строка в `РЕШЕНИЯ.md`: «ИИ-шагов нет, причина».
3. Для каждого изменения шага — **адаптация или перепроектирование** (встраиваем в старый процесс или меняем процесс) — одной строкой, с причиной.

## 3.2 Требования — живой источник правды
`ТРЕБОВАНИЯ.md` проекта ([шаблон](<../templates/Реестр-требований.md>)). Одно требование — одна строка:

| Поле | Правило |
|---|---|
| ID | Т-01, Т-02… — не переиспользуется |
| Формулировка | одно требование, однозначно, **проверяемо** (без «быстро», «удобно», «и т. д.») |
| Источник | ссылка на резюме источника, протокол интервью или решение Р-xx — **без источника требования нет** |
| Приоритет | обязательно / желательно / потом |
| Критерий приёмки | как проверим: «дано — когда — тогда» или конкретная проверка |
| Шаг To-Be и тест | где реализуется и чем проверяется (трассировка) |
| Состояние | черновик → согласовано → утверждено → изменено (ссылка на запрос) / отклонено (причина) |

Нефункциональные требования (надёжность, безопасность, ПД, время ответа, резервные копии) — тем же реестром, по чек-листу [ТЗ](<../templates/ТЗ.md>).

## 3.3 Документ ТЗ
**Источник правды — `ТРЕБОВАНИЯ.md` и To-Be**; документ ТЗ — их **выпуск** с номером версии (v0.1, v0.2… v1.0), собирается в `.docx` по правилам оформления команды.
Форма выпуска — по профилю или по желанию заказчика ([шаблон](<../templates/ТЗ.md>)):
- **ТЗ-лайт** (S, по умолчанию M): 1–4 страницы — цель, границы, требования с критериями приёмки, ограничения, сроки и этапы, что даёт заказчик.
- **ТЗ по структуре ГОСТ 34.602-2020** (L или по требованию заказчика); для систем с ИИ — дополнительно разделы по ГОСТ Р 71752-2024.
Говорить заказчику: «ТЗ составлено по структуре ГОСТ 34.602-2020», а не «соответствует ГОСТ» (СТАНДАРТЫ § 2).

## 3.4 Доработка
1. Выпуск v0.1 → заказчику с короткой сопроводиловкой: что внутри, на что обратить внимание, **срок ответа**.
2. Неясное — **вопросами по одному**, в форме подтверждения: «Делаем так. Согласны — да или нет?». Каждый ответ — сразу в `РЕШЕНИЯ.md` и в реестр.
3. Замечания заказчика — таблица «замечание → решение (принято / отклонено с причиной) → версия» в конце выпуска.
4. **Не больше трёх кругов переписки** — дальше созвон на 30–60 минут по оставшимся вопросам с протоколом.
5. Противоречия между требованиями или с источниками — вопросом, не молча.

## 3.5 Подтверждение и утверждение
- **Согласовано** — заказчик подтвердил раздел или требование (ссылка на письмо или сообщение). Ставится по ходу доработки.
- **Утверждено** — ЛПР заказчика (из паспорта) утвердил выпуск целиком:
  подпись на листе согласования ([шаблон](<../templates/Лист-согласования-ТЗ.md>)) или письменное «утверждаю ТЗ версии 1.0 от ДД.ММ.ГГГГ» в почте или мессенджере;
  подтверждение сохраняется в `Источники\`. Выпуск получает версию **1.0** и дату; файл не меняется.
- После утверждения ТЗ — **базовая версия**: всё, что вне неё, — **запрос на изменение** ([шаблон](<../templates/Запрос-на-изменение.md>)):
  что просят → влияние на сроки и деньги → решение заказчика → выпуск 1.1 → запись `изменение` в журнале.
- Если есть договор — ТЗ его приложение; оплата этапов привязывается к утверждению ТЗ и к приёмке.

## Модули на этом этапе
ИИ — ворота, паспорт каждого ИИ-шага, тестовый набор (собирается **до** первого промпта); ПД — раздел ТЗ «Персональные данные» по модулю;
Канал — требования к боту; Деньги — карта подтверждений денежных шагов; Иностранцы — требования их права.

## Артефакты
To-Be; `ТРЕБОВАНИЯ.md`; ТЗ v1.0 (`.docx`) с подтверждением утверждения в `Источники\`; паспорта ИИ-шагов (флажок ИИ).

## Критерий выхода
ТЗ утверждено (ссылка на подтверждение); у каждого обязательного требования есть критерий приёмки. Запись `решение` «этап 3 → 4».

## Не делать
Не начинать разработку по неутверждённому ТЗ (кроме прототипа «посмотреть» с пометкой). Не менять утверждённое ТЗ без запроса на изменение.
Не вставлять в ТЗ требования без источника.
